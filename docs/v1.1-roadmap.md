# CaptureView 1.1 compatibility and low-overhead roadmap

Version 1.1 focuses on broader USB capture compatibility and lower video-path
overhead. It is not a feature-expansion release. Recording, streaming,
screenshots, multi-source composition, image effects, audio mixing, virtual
camera output, and new third-party media dependencies are out of scope.

## Baseline before 1.1 changes

The current video path is:

```text
Native device format (NV12, YUY2, MJPEG, or RGB32)
  -> Media Foundation Source Reader
  -> Media Foundation video processing / decode to RGB32
  -> contiguous IMFMediaBuffer
  -> CPU copy into the latest-frame vector
  -> UI-thread frame message
  -> UpdateSubresource into a reusable BGRA D3D11 texture
  -> RGB texture sampling and aspect-fit draw
  -> Present(0, DXGI_PRESENT_DO_NOT_WAIT)
```

The selected native media type is set on the Source Reader first. Its output
media type is then explicitly requested as `MFVideoFormat_RGB32` at the selected
width and frame rate. Consequently, NV12 and YUY2 are not yet passed to the
renderer natively, and MJPEG is decoded before the application receives it.

`ConvertToContiguousBuffer` may consolidate a multi-buffer sample. The
application then performs one explicit CPU copy into `VideoFrame::pixels` and
one CPU-to-GPU upload with `UpdateSubresource`. Moving the latest-frame vector
between the capture and UI threads does not copy its payload.

The application retains one unpublished frame only. A new sample replaces that
frame, and at most one frame notification is pending. Rendering occurs on the
UI thread when that notification is handled; there is no continuous render
timer or dedicated render thread. Textures, shaders, views, and the swap chain
are reused while their size and format remain unchanged.

The RGB32 handler currently assumes a tightly packed top-down buffer with
`stride = width * 4`. It validates total buffer length but does not query 2D
stride or account for a negative stride. Existing hardware results establish
that this works for the tested NV12 and MJPEG devices, but it is not yet a
general stride guarantee.

## Ordered implementation plan

1. Verify the existing YUY2-to-RGB32 path on hardware. Fix only defects exposed
   by that validation.
2. Add an NV12 D3D11 native-rendering path while retaining RGB32 fallback.
3. Validate native NV12 rendering across resize, fullscreen, reconnect, and
   representative frame rates.
4. Add and validate a native YUY2 rendering path.
5. Prefer NV12 as Media Foundation's decoded output for MJPEG where supported,
   with RGB32 as fallback.
6. Benchmark one and two processes, then compare Present/VSync behavior.
7. Verify audio-format compatibility without adding a custom resampler or
   mixer.

Each stage must remain independently buildable and preserve the existing
RGB32-compatible path.

## Acceptance criteria

- NV12, YUY2, MJPEG, and RGB32 fallback all display correctly.
- At least NV12 or YUY2 uses GPU color conversion without an intermediate CPU
  RGB conversion.
- 1920x1080 at 60 fps is stable on supporting hardware.
- The latest-frame handoff remains bounded to one unpublished frame.
- Two processes can use two different capture devices concurrently.
- Device disconnect does not crash the application.
- Existing window, settings, overlay, and audio-monitoring behavior regresses
  neither functionally nor visibly.
- The x64 Release build and distribution packages succeed.

The currently tested capture device is suitable for YUY2 compatibility and
layout checks, but its advertised YUY2 modes are bandwidth-limited (800x600/20
and 1920x1080/5 in the validated PC-output tests). At the same 1920x1080 source
resolution, its 10 fps MJPEG mode preserves substantially more text detail than
its 5 fps YUY2 mode. A second USB 3 capture device reproduced similar text
degradation at 1920x1080/20 YUY2 in CaptureView. OBS displays materially sharper
text from that device when explicitly configured for the same YUY2 resolution
and frame rate. This isolates the quality defect to CaptureView's current Media
Foundation conversion/rendering path rather than YUY2 generally or the capture
device. The diagnostic attributes show an exact 1920x1080 progressive path:
native YUY2 has stride 3840 and sample size 4147200, while negotiated RGB32 has
stride 7680 and sample size 8294400. Both use square pixels and 20/1 fps. This
rules out an unexpected resolution, pixel aspect ratio, interlace mode, row
pitch, or sample size and makes the Media Foundation YUY2-to-RGB32 conversion
the leading suspect. Native YUY2 rendering should bypass that conversion while
the RGB32 path remains available as fallback. Neither device is evidence for or
against the 1080p60 performance target; that target requires a device which
advertises a matching native mode.

The first native YUY2 run on `USB3 Video` then passed at 1920x1080/60. Fine UI
text that was visibly degraded by the Media Foundation RGB32 conversion was
restored and measured rendering held 60 fps. The earlier `Queue` overlay field
was an audio metric; dedicated video queue/drop instrumentation was added later.
Full window-mode, color-chart, sustained-run, and reconnect regression checks
remain before final acceptance.

The dedicated video counters were then verified across MJPEG-to-NV12, native
NV12, and native YUY2 at 1920x1080/60. Each reported 60 fps input, 60 fps render,
zero latest-frame replacements, and an empty video slot at the sampled instant.

An initial dual-device run used native NV12 at 1920x1080/60 in one process and
MJPEG decoded to NV12 at 1920x1080/30 in another. The processes independently
reported 60.0/60.0 and 29.8/29.8 input/render fps, cumulative replacements of 9
and 2, and empty video slots. The 48 kHz audio queues sampled between 480 and
960 frames (about 10--20 ms), within the intended bounded queue. A Task Manager
snapshot showed the processes at 1.9%/27.5 MB and 0.2%/31.2 MB CPU/working set.
Total GPU 3D usage was about 6% on the Radeon RX 6600 XT; this is a system-wide
reading that also includes the desktop and other applications. A longer
observation remains.
